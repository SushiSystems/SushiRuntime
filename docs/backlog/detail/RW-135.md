# RW-135 Find why WorkerBufferCache::accept_chunk faults in memmove under load

The row of this entry is in `docs/backlog/DISTRIBUTED_LAYER.md`. This file holds what did not fit the row.

- State: open
- Done when: SushiAI Medium_ClusterRun passes 50 runs in a row under sa test -j 5, and the cause is named in the fix commit

Seen on 2026-11-11 in SushiAI's `sa test -j 5` on a debug tree built with `--distributed`, against
the package `sushiruntime/@a618f4bb5498-sushiai`. The case was
`Medium_ClusterRun.RegressionOneStepFromAFileMatchesTheSingleMachineStep` in
`sushiai_programs_tests.medium_shard_0of2`. The shard passed when it was run alone.

The process stopped with exception code `0xC0000006` on a worker thread of `ThreadDrive::run`
over `InProcessTransport`:

```
VCRUNTIME140.dll           memmove() + 0x1F3
sushiruntime.dll           WorkerBufferCache::accept_chunk(const Wire::BufferChunkMessage&, bool) + 0x182
sushiruntime.dll           (near WorkerAgent::statistics) + 0xDA2
sushiruntime.dll           (near TCPTransport::local_endpoint) + 0xB420
sushiruntime.dll           (near ThreadDrive::ThreadDrive) + 0x10C2
sushiruntime.dll           (near InProcessTransport::worker_index) + 0xEE1
sushiruntime.dll           ThreadDrive::run() + 0x697
```

The frames past `accept_chunk` are export-relative and may be misnamed. The dispatcher warned
just before that every op-tagged node would run locally because no worker was live for the op.
Its known issue is KI-30.
